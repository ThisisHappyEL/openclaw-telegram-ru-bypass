# 🚀 AI Gateway: Local Inference & DPI Bypass

Данный репозиторий является витриной (showcase) инженерных решений, примененных в ходе интеграции open-source проекта [OpenClaw](https://github.com/openclaw/openclaw) (персональный AI-ассистент).

Основной код фреймворка сюда не включен во избежание захламления. Здесь представлены исключительно мои собственные скрипты и конфигурации, написанные для решения сетевых и аппаратных задач.

## 🎥 Демонстрация работы
[🔗 Посмотреть скринкаст с демонстрацией работы и комментариями](https://drive.google.com/file/d/11mXLpJCIZq0zgMhJWx48VDTC6rIDZkGQ/view?usp=sharing)

## 📌 Суть задачи
Необходимо было развернуть AI-шлюз и подключить к нему Telegram-бота, работающего как персональный ассистент с заданным характером (ролевая модель).
**Главные ограничения:**
1. Работа из РФ без использования системного VPN на машине-хосте.
2. Блокировки со стороны зарубежных LLM-провайдеров (HTTP 403 от OpenRouter/OpenAI).
3. Блокировка `api.telegram.org` со стороны российских провайдеров по DPI.

## 🛠 Архитектура решения

Вместо использования стандартных VPN-костылей, я реализовал полностью автономную и отказоустойчивую архитектуру:

### 1. Обход блокировок Telegram API (Cloudflare Workers)
Для связи Gateway с серверами Telegram я написал и развернул бессерверный reverse-proxy на базе **Cloudflare Workers** (`cloudflare-worker.js`). 
В конфигурации OpenClaw штатный `apiRoot` был подменен на адрес моего воркера. Это обеспечило мгновенный отклик Telegram-бота без необходимости туннелировать весь трафик сервера.

### 2. Локальный инференс LLM (Ollama + CUDA)
Для решения проблемы санкционных блокировок облачных LLM-провайдеров, я перевел агента на полностью локальный инференс.
- **Среда:** Ubuntu (WSL2)
- **Движок:** Ollama 
- **Модель:** Qwen 2.5 (7B)
Шлюз был напрямую интегрирован с Ollama, а использование мощностей GPU (RTX 4080) позволило добиться скорости генерации ответа в ~1-2 секунды, что превосходит облачные бесплатные аналоги. Дополнительно был отключен избыточный набор инструментов (Profile: `minimal`), чтобы избавить модель от перегрузки контекста.

### 3. Инъекция персонажа (SOUL.md)
Для выполнения требований к ролевой модели (Tone of Voice) был составлен системный промпт `SOUL.md`. Использование метода Few-Shot Prompting (предоставление примеров диалога) помогло модели строго удерживать образ и игнорировать попытки выхода из роли.

## 📂 Содержимое репозитория
* `cloudflare-worker.js` — код бессерверной функции для проксирования Telegram API.
* `SOUL.md` — системный промпт и настройки характера ассистента.
* `openclaw-config-snippet.json` — выдержка из конфигурации шлюза, демонстрирующая связку с локальной моделью и Cloudflare-прокси.

**Стек:** TypeScript/JavaScript, Cloudflare Workers, WSL2, Ollama, LLM (Qwen 2.5).

## 🛠 Журнал отладки (Troubleshooting Journey)
В ходе выполнения задачи я столкнулся с рядом инфраструктурных вызовов, которые потребовали глубокого погружения в работу сетей и архитектуру OpenClaw. Ниже описан процесс их решения:

1. **Диагностика сетевых ограничений (DPI)**
   При первоначальном запуске шлюз циклически падал с ошибкой `UND_ERR_CONNECT_TIMEOUT` при обращении к Telegram. 
   С помощью утилит `curl` я изолировал проблему: проверил доступность обычного интернета из WSL2 (`curl -I https://ya.ru` -> 200 OK) и доступность API Telegram (`curl -4 -I https://api.telegram.org` -> Timeout). Это доказало наличие глубокой блокировки (DPI) со стороны провайдера, а не баг маршрутизации WSL + VPN. Решением стал Cloudflare Worker.

2. **Анализ исходного кода (Reverse Engineering)**
   Чтобы понять, как "подсунуть" свой прокси в OpenClaw, я не стал ждать ответа от поддержки, а проанализировал кодовую базу через консоль:
   `grep -ri "api.telegram.org" .` и `grep -rn "agent model:" src/`. 
   Это позволило мне быстро найти скрытые в исходниках переменные `apiRoot` и нужные форматы для `modelRef`, чтобы переопределить их в `openclaw.json`.

3. **Борьба с галлюцинациями моделей (Attention Latching)**
   Изначально я запустил легковесную модель `qwen2.5:0.5b`. Однако при передаче ей системного контекста на 40+ инструментов (tools), модель не справлялась с объемом инструкций и начинала выводить системные JSON-теги прямо в чат. 
   **Решение:** 
   - Отключение избыточных инструментов в конфиге (`"profile": "minimal"`).
   - Очистка кэша SQLite-сессий (`rm -rf ~/.openclaw/agents/main/sessions/*`), чтобы модель перестала "якориться" за свои старые ошибки.
   - Переход на более взрослую модель `qwen2.5:7b`, которая идеально обрабатывает Few-Shot Prompting на русском языке и полностью помещается в VRAM RTX 4080.

4. **Работа с Linux-окружением**
   В процессе установки локального инференса пришлось на лету донастраивать окружение Ubuntu в WSL2 (например, ставить отсутствующий `zstd` для распаковки пакетов Ollama) и управлять версиями Node.js через `nvm` для корректной компиляции зависимостей.
